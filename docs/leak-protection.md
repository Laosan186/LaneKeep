# 防泄漏机制与边界

[English](leak-protection.en.md) · [返回 README](../README.md)

本文描述当前源码中的机制，包括 v0.2.0 加入的自定义 IP 规则，以及 0.2.1 之后尚未发布的防泄漏加固（见 [CHANGELOG](../CHANGELOG.md) 的 Unreleased 段）；已发布的 0.2.1 安装包不含这些加固。机制存在不等于所有终端、应用和网络条件已经验证。默认安装处于停用状态；下面的流量保护只在用户明确启用后运行。

## 固定规则矩阵

| 规则 | 常规 | 全局 | 增强 | 按需代理 |
|---|---|---|---|---|
| TCP/UDP 53 交给共享 DNS | 有 | 有 | 有 | 有 |
| 目标端口 853 阻断 | 有 | 有 | 有 | 有 |
| `geosite:category-doh` 阻断 | 有 | 有 | 有 | 有 |
| 内部 DNS / 透明代理端口保护 | 有 | 有 | 有 | 有 |
| 未还原 FakeIP 地址阻断 | 有 | 有 | 有 | 有 |
| UDP 443 | 全部阻断 | 全部阻断 | 全部阻断 | 指定服务分类及自定义代理域名和 IP |
| iCloud Private Relay 分类阻断 | 无单独条目 | 有 | 无单独条目 | 无单独条目 |
| 发往私有地址（`geoip:private`）的 UDP | 直连 | 阻断 | 阻断 | 直连 |
| 其余 UDP（自定义规则之后） | 按后续规则 | 走代理 | 全部走本模式代理，不直连 | 按后续规则 |

矩阵来自 `root/etc/lanekeep-proxy/template.json` 和生成器。FakeIP 规则包含 `198.18.0.0/15` 与 `2001:2::/48`；软件接管范围是 IPv4，不能因 JSON 里出现 IPv6 范围就宣称已保护 IPv6。已还原为域名的合法 FakeDNS 流量按域名继续匹配。

固定保护在自定义规则之前；部分私有域名和私有地址直连也在自定义插入点之前。按需模式的 IP 分类不能扩写为所有 UDP 443 都受阻断。

## 自定义 IP 规则

规则类型“IP / 网段”只接受一个公网 IPv4 地址或网段，例如 `1.2.3.4` 或 `1.2.3.0/24`；`/32` 按单个地址保存，网段的主机位必须为 0。与以下范围有任何重叠都会被拒绝：`0.0.0.0/8`、私网、`100.64.0.0/10`、本机、链路本地、`192.0.0.0/24`、文档地址、FakeIP 所在的 `198.18.0.0/15`、组播与保留段，以及从 OpenWrt 读取的所选 LAN 子网。因此 IP 规则不会覆盖局域网或 FakeIP 池，固定保护仍排在自定义规则之前。

- Xray 同一条规则里的 `domain` 与 `ip` 是“且”关系，所以 IP 规则总是单独成行；相邻且出口相同的 IP 规则合并为一行。
- 路由使用 `domainStrategy: AsIs`，入口开启 FakeDNS 与 TLS/HTTP/QUIC 嗅探。能识别出域名的连接按域名匹配，**IP 规则只命中直接连接 IP 且识别不出域名的流量**，例如部分应用、游戏或指定服务器。用浏览器打开网站测不出 IP 规则，网站请用域名规则。为保持现有保护，本功能不改动 `domainStrategy`。
- 字面 IP 流量没有 FakeIP 防护，因此 IP 规则的出口不能是两跳链：既不能指定链，也不能在本模式的节点是链时使用“本模式的节点”。
- 按需模式中出口为代理或指定节点的 IP 规则，会先生成相同目标的 UDP 443 阻断行，与自定义代理域名的处理一致。
- 要把所选 LAN 改到与已保存 IP 规则重叠的网段，先在面板修改或删除这些 IP 规则并应用，再改网段。若已先改了网段，生成配置会失败并保持原有运行配置，面板也无法应用删除规则的改动；需先把 LAN 改回原网段，删除规则并应用后再改。
- 0.1.0 的生成器不认识 IP 规则。降级回 0.1.0 前，先在面板删除全部 IP 规则并应用。

## DNS

启用后 nft 捕获所选 LAN 的 IPv4 TCP/UDP 流量，53 端口在管理端口例外之前交给透明入口。Xray DNS 使用 FakeDNS 和受保护真实解析，不允许失败后使用系统 hosts 或普通 DNS 回落。

受保护真实解析通过默认节点访问 Cloudflare DoH，主地址 `1.1.1.1`，备地址 `1.0.0.1`。健康域名 `one.one.one.one` 的主、备查询超时分别为 800 ms 和 900 ms；健康条目禁用缓存。每个模式可以更换数据出口，但共享 DNS 不随各模式节点更换。

常规模式的国内域名分类保留系统解析链；启用时保存原 dnsmasq 字段，再使用本包回环 DNS 服务（5053，阿里 DoH）。该服务是独立的 Xray 实例，使用 IPv4 加密上游，不需要安装会自动接管 DNS 的第三方 DNS 管理服务。常规模式其他公网域名通过受保护解析封装处理，出口仍按规则决定；“DNS 走代理”不等于“数据必定走代理”。

FakeIP 例外出厂为空，可添加 `domain:` 或 `full:` 项。例外只决定是否使用真实解析，不能自行改变设备的数据出口。不得把 DNS 测试结果所在国家当作唯一泄漏判据。

## WebRTC、UDP 和 IPv6

透明 TCP/UDP 与路由规则共同决定出口。命中代理的 WebRTC 流量使用代理出口；命中直连的目标会看到直连公网地址。未知 DoH、显式直连例外和应用行为不在绝对保证范围内。

Xray 的透明 UDP 按源套接字建立会话：同一个套接字发出的第一个包决定出口，之后发往其他目标的包沿用它。所以一个套接字只要先命中直连，后面发往任何 STUN 服务器的包都会从直连出口出去。0.2.1 及更早版本里，全局和增强模式的私有地址直连、增强模式的国内分类直连都会触发这种情况。0.2.1 之后的做法：

- **全局和增强模式**：发往私有地址（含 `100.64.0.0/10`）的 UDP 阻断，排在私有地址直连之前。局域网内同网段设备互访不经过路由器，不受影响；经路由器转发到其他私有网段的 UDP，以及发往路由器 LAN 地址的非 DNS UDP（例如路由器上的 NTP），在这两个模式下不可用。TCP 不变。
- **增强模式**：自定义规则之后的全部 UDP 走本模式的代理节点，不再因为目标属于国内分类而直连。国内语音视频通话、游戏等 UDP 业务会经代理出口，延迟上升，也可能失败；需要国内 UDP 直连的设备请放在常规或按需模式。TCP 仍按国内分类直连。
- **仍然会暴露直连地址的情况**：增强模式下，被归为国内的目标经 TCP 直连，包括 TURN over TCP/TLS、任意国内地址上的 DoH 或 HTTPDNS，以及普通 HTTPS。网页可以自行选择这样的目标并读到直连地址，所以增强模式不能当作“不暴露直连地址”使用；需要这一点请用全局模式。自定义直连规则同理，而且一个套接字先命中自定义直连规则后，后续 UDP 也走直连。自定义直连域名由国内解析链解析。
- **全局模式也有一条已知的直连路径**：内置的“私有域名直连”规则按域名匹配，而 `geosite:private` 里有一些会解析到公网地址的域名（例如 `plex.direct`、`ts.net` 和部分路由器厂商的域名）。访问这类域名的 HTTP 和 TLS 连接在全局和增强模式下走直连，对方能看到直连地址；网页也可以主动连接这类域名。这条规则保持原样，是为了让这类本地服务继续直连。
- 常规和按需模式默认直连，上述两条规则不适用，套接字沿用出口的行为保持不变。

本包不关闭或重配 IPv6。管理员需要提前关闭所选 LAN 的 IPv6 地址、RA / DHCPv6，并禁用对应设备 IPv6，而且要保存为开机设置；启用前检查不满足就拒绝。仅关闭 RA 不够。卸载不会撤销管理员自己做的 IPv6 设置。

启用之后这个前提继续生效：看门狗每轮读取 LAN 设备的 `disable_ipv6`，不为 `1` 或读不到时保护门控保持关闭，状态页给出提示。启用期间的阻断表还会丢弃从 LAN 设备转发的全部 IPv6，以及发给路由器自身的 IPv6 DNS。这些只管经过本路由器的流量：同一二层上的其他设备（例如 AP 或光猫）下发的 IPv6 不经过本路由器，需要在那台设备上关闭。

## 断线保护

启用期间有一张独立的 nft 表 `lanekeep_guard`，保存在 `/etc/lanekeep-state/boot-guard.nft`，由 `lanekeep-guard` 启动脚本在网络和防火墙启动之前载入。它丢弃从所选 LAN 子网转发的 IPv4、从 LAN 设备转发的 IPv6，以及没有被透明入口接管的 LAN DNS 请求。被接管的流量在路由器本机投递，不受它影响。因此在下列时候局域网设备不会改走直连，而是没有网络：

- 开机后到 LaneKeep 启动完成之前；
- 开机时检查不通过或启动失败（启用标记保持为 1）；
- 运行时被 `stop`；
- 软件包升级期间。这一条从包含这次加固的版本起成立：从 0.2.1 或更早版本升级的那一次，旧版的升级脚本会先撤掉规则，到新版装好之前局域网是直连的。

路由器管理页面仍可访问。只有明确停用（或卸载）才移除这张表；在面板里手动启用失败时回到停用状态。

数据出口标记 `0x7621`，DNS 探测出口使用独立标记。nft 的 `healthy_data` 是最长 8 秒的租约。看门狗每轮执行有界 DNS 探测，轮后休眠 2 秒；探测连同锁等待超过 3 秒视作失败。连续两轮成功才开放并续租；失败清空租约，进程停止后旧租约自行过期。

这是有延迟的失效关闭机制，不是零时延检测，也不是对任意目标的完整连通检测。它跟随默认节点，并限制其他节点承载的代理数据。不会自动换节点或改成直连。直连业务仍依赖核心和 DNS，不能保证故障时持续可用。

切换默认节点的活动事务保存旧配置，最多等待约 60 秒验证新的门控、核心身份和规则状态。失败尝试恢复并重新验证旧状态；恢复仍失败则保留阻断。未启用时的保存不启动这条网络事务。

## 日志和数据

生成配置明确设置 `access: none`、`error: none`、`loglevel: none`、`dnsLog: false`；本包 DNS 实例也关闭这些日志。系统仍可能记录服务启动或故障，不承诺整台 OpenWrt 没有日志。

监控记录聚合数字、类别与有限的故障/操作摘要；逐连接目标只在采集调用内暂存，不写入浏览历史。节点、订阅及回退快照含凭据，使用受限权限保存；“不记浏览日志”不等于“没有敏感配置”。

## 专用入口

10811–10860 为 LAN SOCKS5 入口，限全局、增强、按需模式，按源 IP 成员限制访问。入口使用其自身选定出口，有私有地址、内部端口、53/853 等阻断规则；不继承模式的全部业务规则或广告规则。TCP 链默认仅承载 TCP，UDP 需相应能力与明确启用。

## 自己验收

1. 先在独立测试环境安装，确认停用时 DNS、nft 和策略路由没有被接管。
2. 配置节点、模式、IPv6 前提并明确启用；检查状态和规则核对结果。重启一次，确认 IPv6 设置在开机后仍然生效、LaneKeep 正常启动。
3. 分别测试代理目标、直连目标、DNS、WebRTC 和应用自带加密 DNS；记录模式与规则。
4. 在测试环境主动中断默认节点，观察门控延迟与恢复；不要用一次成功推断所有故障场景。
5. 停用或卸载，核对原 DNS、策略路由和本包 nft 表恢复情况。
